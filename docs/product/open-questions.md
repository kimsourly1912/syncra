# Open questions

These are unresolved product, permission, and contract questions. An open question doesn't authorize behavior. Build only what doesn't depend on the answer, and don't code a guess. When a question is answered, record the answer in the doc that owns the rule (scope, feature reference, or app docs) and delete it here.

Known code defects aren't questions. They're listed under **Known gaps** in each app's `docs/architecture.md`.

## Admin

| Question | Blocks | Evidence that would settle it |
| --- | --- | --- |
| Which account actions are wired to the service? The account list now reads `GET /admin/portal-users`, but its Add Member and Create Company Admin dialogs are static. Account Detail reads `/admin/portal-users/{userId}/account-detail` (summary and company information); there are no read endpoints for an account's modules, seats, or members, and `GET /admin/companies/{companyId}/credits/history` returns purchases with an undocumented `pageable` query, so those tabs show sample data. | Wiring account actions and Account Detail's Modules, Tokens, and Seats tabs | The Admin API contracts and a staff test environment |
| Who sets a new company admin's temporary password, and which role ID is Company Admin? `POST /admin/portal-users/company-admin` takes email, names, `roleId`, and `company.companyName` but no password, and returns `password`, so the API seems to generate it. Admin's Create Company Admin dialog (UI only) lets staff type or generate one and previews the success step from the form. There's no roles endpoint to look up `roleId`. Is the password emailed to the admin, and can staff see it again or only reset it (`POST /admin/users/password/set`)? | Wiring Create Company Admin; whether the success step must warn that the password is shown once | The API owner's create-admin contract, checked with a test company |
| How do Admin lists page, sort, and filter? `GET /admin/lead-inquiries`, `/admin/portal-users`, and `/admin/sale-requests` take `search`, `sort`, `page`, and `size`, but the spec doesn't give the `sort` format or fields, the largest `size`, or whether `search` matches names, emails, or companies. The lists offer 20, 50, and 100 rows per page and no sorting. `GET /admin/portal-users` has no onboarding-status filter (for example `onboardingStatus=COMPLETED|PENDING`), so Account Management shows its status filter disabled until the API adds one. Portal-user rows carry `companyId` but no company name. | Sortable columns; confirming 100 rows is allowed; an Onboarding Status filter; showing company names | The API owner's paging and sorting contract, and a decision on the onboarding-status filter and company name |
| How do the list totals map to statuses? Lead `/summary` returns `leadReceived`, `contacted`, `converted`, and `rejected`, but lead statuses are `NEW`, `CONTACTED`, `CONVERTED`, and `NOT_INTERESTED`. Is `rejected` the same as `NOT_INTERESTED`, and is `leadReceived` all leads? Sale request `/dashboard` has `total`, `pending`, `approved`, and `rejected`, but no `completed`. The Sale Request and Lead Inquiry lists show the totals as status-tab counts, matching by name (`total`→All, `leadReceived`→All, and `pending`, `approved`, `rejected`, `contacted`, `converted` to the tab of the same name); New, Not interested, and Completed have no count. | Confirming the tab counts are right | The API owner's definition of each total |
| Should a refused session refresh return 401? `POST admin/auth/refresh` without a valid refresh cookie answers HTTP 500 with `success: false` (`refreshToken blank`), so the client treats any `success: false` body as refused ([0008](../decisions/0008-admin-api-client-and-session.md)). A temporary fault reported the same way (database or Cognito down) therefore signs staff out. Does the API rotate refresh tokens, and does it detect reuse? | Dropping that special case; tuning the cross-tab renewal lock | The API owner's refresh contract |
| Does `POST /admin/auth/logout` revoke the refresh token on the server and clear both cookies? Admin now renews an expired access token before logging out ([0014](../decisions/0014-admin-session-survives-api-outages.md)), but a logout that only clears cookies leaves a stolen refresh token usable. | Trusting sign-out on shared computers | The API owner's logout contract, checked with a staff test account |
| What can `POST /admin/auth/login` answer besides a session? `LoginResponseView` has `pass`, `userStatus`, `session`, and `cognitoJWT` (id, access, and refresh tokens), and the spec has `/admin/auth/otp/request` and `/otp/verify`. Admin ignores the body, so a challenge (for example a new-password step for staff invited with a temporary password, or an OTP) would show only "Signed in, but your profile could not be loaded". If the body really carries the tokens, JavaScript can read them, which undoes HttpOnly cookies. | Invited staff's first sign-in; MFA; removing tokens from the body | The API owner's login contract and an invited staff test account |
| Does `GET /admin/auth/forgot-password/verify` only read the token, or does it use it up or start a timer? The reset page calls it on load to name the account and catch a bad link before the form, and again when a reset is refused; if it consumed the token, the confirm would fail. Which refusals mean "expired" and which "already used"? Admin shows any refusal as "This link can't be used". | Trusting the reset page's link check | The API owner's contract, and a test account's reset link opened, then confirmed |
| How are the Admin session cookies scoped and flagged? They're set on `.syncra.app`, and CORS accepts every `*.syncra.app` origin, so an XSS bug on Web or Portal could call the Admin API as staff. Are they `HttpOnly`, `Secure`, and `SameSite`? Do Portal and Admin cookie names collide? | Narrowing cookies to the Admin host and CORS on `/admin/*` to the Admin origin | The API's cookie and CORS settings per environment |
| Do sign-in and forgot-password reveal whether an email is a staff account? Admin shows the API's `reason` on a refused sign-in, and `sent: false` as "We couldn't send a reset link to this address". | Account-enumeration hardening | The API's answers for a known and an unknown email |
| Which security headers does the Admin host send? A staff console needs a CSP with `frame-ancestors 'none'` (clickjacking on Approve and Disable) and a `Referrer-Policy`. The hosting config isn't in this repository. | Header hardening | The deployment config for each environment |
| What is Community Management (`/community`) for, and who may use it? It has no requirement and the API has no endpoints for it, so it shows a placeholder listing what's needed. Settings (`/setting`) is built from the endpoints that exist, but the API has no list of staff accounts (staff access works by email), what an invitation's temporary password is for isn't documented, and who may edit email templates (`PUT /admin/email-templates`, template mappings) isn't confirmed, so templates and token packages are read-only. Sale Request lists requests and shows one read-only in a side panel (`GET /admin/sale-requests/{id}`); what approving, rejecting, or completing one does (and who may) isn't specified, nor which detail fields each request type fills. | Building those screens; sale request actions | A product decision, and the API contracts |
| What are the endpoints, validation, and permissions for products, plans and pricing, hero content, and changing a lead's status? The product and plan pages (list, create, and edit, all on sample data) and the hero page are UI shells with no submit wiring; deactivate and delete are shown but off. Leads open read-only in a side panel from `GET /admin/lead-inquiries/{id}`. `POST /admin/lead-inquiries/change-status` takes a status and a `reason`, but which changes are allowed, whether a reason is required, and who may make them aren't specified. | Building Admin CRUD for them; lead status actions | The Admin API contracts |
| Which response fields are always present and non-null? The OpenAPI spec declares `required` on 24 of 330 schemas, marks no field nullable, documents no error responses, and leaves the date-time format unverified. Admin guards this with feature models ([0007](../decisions/0007-generated-api-contract.md)). | Tightening generated types; enforcing formats | A spec with `required`/`nullable` set, or confirmed sample responses from the API owner |
| What is the real shape of TechPack inspection findings? The spec has a single `Finding` schema (with `aiValue`) for both PDF and AI findings, probably because springdoc collapsed two classes with that name. Admin reads `pdfValue` on PDF findings, based on the working review screen (`features/techpack-review/models/workbook-inspection.ts`). Inner classes named `Result` and `Sheet` suggest the same naming issue. | Trusting the generated inspection types | Distinct schema names in the spec (for example `PdfFinding`/`AiFinding`), or a confirmed sample response |
| Which error-reporting service should Admin send errors to, and what may an error report contain? Today `reportAppError` (`src/admin/app/utils/report.ts`) only logs to the staff member's console, so API contract drift and uncaught errors in production are invisible to the team. | Connecting `setErrorReporter`; alerting on contract errors | A chosen service and its project, plus a data-handling rule (no credentials or customer documents in reports) |
| What format does `Overview.registeredDate` (`GET /admin/portal-users/{userId}/account-detail`) use? The spec gives no `format`. Admin shows a bare `YYYY-MM-DD` as that calendar day, and anything else as a timestamp in the reader's time zone. | Trusting Account Detail's Registered date | A sample response, or a `format` in the spec |
